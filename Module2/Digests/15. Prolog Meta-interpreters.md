In Prolog, no difference between programs and data, or, using the Prolog terminology, …==No difference (in the representation) between predicates and terms==.

In Prolog, a meta-interpreter for a language L is defined as an interpreter for L, but written in Prolog. 

Meta-interpreters can be seen as meta-programs, i.e., programs who execute/works/deal with other programs.  Programs as input of meta-programs. 

Given the premises, would it be possible to write a Prolog interpreter for the language Prolog?

# Vanilla meta-interpreter Prolog
Define a predicate solve(goal) that answers true if Goal can be proved using the clauses of the current program \[==IT'S his most asked question at the exam==\].
```
solve(true) :- !. 
solve( (A,B) ) :- !, solve(A), solve(B).
solve(A) :- clause(A,B), solve(B).
```
(The comma in prolog is intended as the conjuction of something). 

With these 3 lines, we have indeed made an interpreter for Prolog in FOL, that __uses SLD__.

Notice: no need to "call" any predicate. The vanilla meta-interpreter explores the current program, searching for the clauses, until it can prove the goal, or it fails. 
As it is, the vanilla meta-interpreter mimic the standard behaviour of the Prolog interpreter, and we can modify it and get different behaviours.

i.e., we can define a Prolog interpreter that adopts the right most policy:
```
solve(true) :- !. 
solve( (A,B) ) :- !, solve(B), solve(A). // We switched order of rules
solve(A) :- clause(A,B), solve(B).
```

### Exercise example 1
Define a Prolog interpreter solve(Goal, Step) that: 
- It is true if Goal can be proved 
- In case Goal is proved, _Step is the number of resolution steps used to prove the goal_. In case of conjunctions, the number of steps is defined as the sum of the steps needed for each atomic conjunct. 

For example:
![[example_step_prolog.png]]

The code for such thing would be:
```
solve(true,0) :- !. 
solve((A,B),S) :- !, solve(A,SA), solve(B,SB), S is SA+SB. 
solve(A,S) :- clause(A,B), solve(B,SB), S is 1+SB.
```

### Exercise example 2
Let us suppose to represent a knowledge base in terms of rules, and for each rule we have also a "certainty" score (between 0 and 100).
![[certainty_score_example.png]]
Define a meta-interpreter `solve(Goal,CF)`, that is true if Goal can be proved, with certainty CF.
For conjunctions, the certainty is the minimum of the certainties of the conjuncts. 
For rules, the certainty is the product of the certainty of the rule itself times the certainty of the proof of the body (eventually divided by 100).
```
solve(true,100) :- !.
solve((A,B),CF) :- !, solve(A,CFA), solve(B,CFB), min(CFA,CFB,CF).
solve(A,CFA) :- rule(A,B,CF), solve(B,CFB), CFA is ((CFB*CF)/100).
min(A,B,A) :- A<B,!.
min(A,B,B).
```

# `assert` and `retract` - Modifying programs
When a Prolog program is consulted/loaded, its representation in terms of data structures (terms) is loaded into a table in memory.
Such table is often referred as the _program database_. Indeed, it is managed using DBMS techniques for increasing performances (For example, functors of the heads are indexed, to speed-up the search for possible candidates for unification with a goal). 

For this reason, we can change it. 
`assert(T)`: Clause T is added to the database program.
When assert is evaluated, ==T must be instantiated to a term denoting a clause (either a fact or a rule, so NOT A NUMBER, but something that can be evaluated as either true or false)==. T is added to the database program in a nonspecified position. 

==In backtracking, ___assert___ is ignored==:
- Non declarative behaviour 
- Added clauses are not removed by backtracking 
- For efficiency reasons, functors of predicates that will be added must be declared as "_dynamic_“: `:- dynamic(foo/1))`.

However, since the order of the clause definitions in Prolog does have a (important!) meaning, there are two variations available:
- `asserta(T)`: T is added at the beginning of the database 
- `assertz(T)`: T is added at the end of the database 
![[assert_example.png]]

`retract(T)` is the complementary clause to assert. The first clause in the database that unifies with T is removed.
When evaluated, T should be instantiated to a term denoting a clause. 
If more than one clauses unify with T, the first one is removed; some Prolog implementations keep tracks with a backtrackable choice point.

### Issues with retract and assert
Consider an empty program, and the following queries: 
```
?- assert(p(a)), p(a).
?- p(a), assert(p(a)).
``` 
The first query succeeds; the second query fails. That is because assert is ignored in the backtracking. 

A further problem is about the quantification of variables.
- Variables in clauses are quantified universally… 
- Variables in queries are quantified existentially.  

Consider the query `:- assert((p(X))).` 
- X is existentially quantified. 
- However, the database is extended with the clause p(X). 
- the final formula is, then, ∀X p(X)
